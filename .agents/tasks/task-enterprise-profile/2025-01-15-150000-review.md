# Enterprise profile management: 2FA, sessions, activity, and settings UI

This change adds a full enterprise profile management surface to both the backend and frontend. The backend gains 17 new API endpoints under `/api/profile` covering TOTP-based two-factor authentication, session management, login/security activity feeds, notification preferences, cloud account linking, data export, and account deletion. The frontend replaces the existing Profile page with a tabbed settings experience (11 tabs) including 2FA setup flow with QR codes, session revocation, activity timelines, and a danger-zone account deletion flow. A fire-and-forget presence middleware stamps `lastSeenAt` on each authenticated request.

**Watch for:** The "revoke all other sessions" logic hashes the **access token** to identify the current session, but the Token model stores hashes of **refresh tokens** — so the exclusion filter will never match and all sessions (including the caller's) get revoked (confirmed). Backup codes are accessible via a GET endpoint without re-authentication, making them available to any stolen access token (confirmed). The presence middleware issues an unindexed `updateOne` on every authenticated profile request with no debounce (confirmed).

## High-level view

The session management design has a fundamental identity mismatch: it tries to exclude the current session during "revoke all others" by hashing the access token from the Authorization header, but the Token model stores only refresh token hashes. The `$ne` filter compares different token types and will always delete all sessions. The same issue means no session can ever be marked as "current" in the getActiveSessions response.

Security-sensitive endpoints (disable 2FA, delete account) require password re-verification and are rate-limited. However, viewing backup codes and the 2FA setup initiation endpoint are unprotected beyond the session token, which weakens the security model for compromised sessions. The setup endpoint also overwrites backup codes on each call without rate limiting.

The presence middleware fires a write on every authenticated profile request with no throttle. Under concurrent load this adds unnecessary write pressure to MongoDB with silently-dropped errors.

The account deletion flow records the audit log *after* anonymizing the email, losing the original email in the audit trail.

The frontend is a 1050-line single-file component. Several tab components include `notify` in their `useEffect` dependency arrays — if the `useNotification` hook doesn't return a stable reference, this causes infinite re-fetch loops.

The User model now has both `preferences.emailNotifications` (pre-existing) and `notificationPreferences.emailNotifications` (new) with no migration path, so the two locations can drift.

## Session identity mismatch and the "current session" problem

The `revokeAllOtherSessions` controller extracts `req.token` — which is the **access token** from the `Authorization: Bearer` header — then SHA-256 hashes it and passes it as `currentTokenHash` to the service:

```javascript
// profile.controller.js
const currentToken = req.token;
const currentTokenHash = currentToken
  ? crypto.createHash('sha256').update(currentToken).digest('hex')
  : null;
```

The service uses this hash in a `$ne` filter against the Token model's `tokenHash` field:

```javascript
// profile.service.js
if (currentTokenHash) {
  query.tokenHash = { $ne: currentTokenHash };
}
```

But the Token model only stores hashes of **refresh tokens** (created during login/token rotation in `token.service.js`). Access tokens are JWTs verified against a secret and never stored. The hash of an access token will never equal any stored `tokenHash`, so the `$ne` condition is always true for all documents, and `deleteMany` removes everything — including the session the user is currently on.

The same gap affects `getActiveSessions`: the controller comment says "controller will mark the current one" but there's no mechanism to do so, since the access token can't be correlated back to its refresh token document. Every session renders as `current: false`.

To fix this properly, the refresh token (from the cookie or request body) needs to be available to the controller, or the Token model needs a secondary identifier (like a session ID) that both the access token payload and the stored document share.

## Backup codes and 2FA setup without re-authentication

The `GET /2fa/backup-codes` endpoint returns all unused backup codes to any authenticated request. In a scenario where an attacker obtains a valid access token (XSS, token leak), they can retrieve the backup codes and use them to bypass 2FA on future logins. Most enterprise 2FA implementations require password re-entry or a current TOTP token before revealing backup codes.

`POST /2fa/setup` overwrites the existing `twoFactorSecret` and `twoFactorBackupCodes` fields every time it's called (it checks `twoFactorEnabled` but not whether a pending setup already exists). A malicious actor with a stolen token could repeatedly hit this endpoint to overwrite backup codes, effectively performing a denial-of-service on the legitimate user's 2FA recovery path. This endpoint also lacks rate limiting (unlike disable2FA and deleteAccount which have `authLimiter`).

## Presence middleware: write amplification without throttle

```javascript
export function updatePresence(req, _res, next) {
  if (req.user?.id) {
    User.updateOne({ _id: req.user.id }, { lastSeenAt: new Date() }).exec();
  }
  next();
}
```

Every single profile endpoint hit triggers a write to the users collection. A user clicking through activity pages or toggling notifications fires a write on each request. Errors from these writes are silently dropped (no `.catch()` on the exec promise). Mitigation: only update if `req.user.lastSeenAt` is older than 60 seconds.

## Account deletion: audit log records anonymized email

In `deleteAccount`, the user's email is overwritten to `deleted_${user.id}@deleted.local` before the audit log is recorded:

```javascript
user.email = `deleted_${user.id}@deleted.local`;
await user.save();

await auditLogRepository.record({
  actor: user.id,
  actorEmail: user.email, // <-- this is now the anonymized email
  ...
});
```

The audit log loses the original email, making it impossible to trace which actual account was deleted.

## Frontend: `notify` in useEffect dependency arrays

Several tab components pass `notify` as a dependency to `useEffect`:

```javascript
useEffect(() => {
  profileService.getActiveSessions()
    .then(setSessions)
    .catch((err) => notify.error(getErrorMessage(err)))
    .finally(() => setLoading(false));
}, [notify]);
```

If `useNotification()` returns a new object on each render, every tab that fetches data on mount will re-fetch indefinitely. This pattern appears in SessionsTab, LoginActivityTab, CloudAccountsTab, and SecurityActivityTab.

## Notification preferences: dual storage locations

The User model now has both `preferences.emailNotifications` (pre-existing) and `notificationPreferences.emailNotifications` (new). The frontend initializes from the new location with fallback to the old:

```javascript
emailNotifications: user?.notificationPreferences?.emailNotifications 
  ?? user?.preferences?.emailNotifications ?? true
```

Writes go only to `notificationPreferences`. The pre-existing `preferences.emailNotifications` is never updated or migrated. Any code that reads from the old location will see stale values after the user saves notification preferences through the new UI.
