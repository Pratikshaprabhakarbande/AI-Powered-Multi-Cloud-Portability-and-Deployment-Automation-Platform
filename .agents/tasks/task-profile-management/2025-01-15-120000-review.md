# Profile management: avatar upload, email change, password change

The change adds a full profile management module: a new `/api/profile` route group with dedicated endpoints for avatar upload (base64 data URL stored in MongoDB), email change (with password verification and session revocation), and password change (with complexity validation). The frontend receives a rewritten Profile page split into four independent forms (avatar, details, email, password), a reusable `AvatarUpload` drag-and-drop component, and Navbar avatar display. The global JSON body-size limit was raised from 1 MB to 10 MB to accommodate base64-encoded images.

**Watch for:** The global body-size increase to 10 MB affects every endpoint, not just avatar upload (confirmed). The `confirmPassword` field is accepted but never validated server-side against `newPassword` (confirmed). The password-change and email-change endpoints accept password guesses without the `authLimiter` applied, unlike `/auth/login` (confirmed).

## High-level view

The backend introduces three new service functions (`changeEmail`, `changePassword`, `uploadAvatar`) wired through the existing auth controller and a new `/api/profile` route file. These duplicate the routing pattern already present in `/api/auth/profile` — the old endpoints remain, so there are now two ways to update profile fields with subtly different validation schemas.

Avatars are stored as full base64 data URLs in the `avatarUrl` field of the User document. Every `user.toJSON()` response — login, token refresh, profile fetch — now potentially carries a multi-megabyte string, inflating every authenticated API call.

The email-change and password-change endpoints sit behind the general `apiLimiter` rather than the stricter `authLimiter` used for login and reset. Since both accept a `currentPassword` field for hash comparison, they are brute-force surfaces with weaker throttling.

The frontend password-strength validation uses a broader special-character regex than the backend, which can cause the UI to show "all requirements met" while the server rejects the password.

## Global body-size escalation

The diff changes `express.json({ limit: '1mb' })` in `app.js` to `express.json({ limit: '10mb' })`. This affects every route in the application — dashboard, terraform, security, compliance — all of which have no reason to accept payloads larger than 1 MB. The avatar route already applies its own `express.json({ limit: '10mb' })` middleware locally in `profile.routes.js`, making the global bump redundant for its intended purpose and harmful everywhere else. A malicious client can now POST 10 MB to any endpoint, amplifying memory pressure on the Node process.

```js
// profile.routes.js already does this per-route:
router.post('/avatar', express.json({ limit: '10mb' }), validate(...), authController.uploadAvatar);
```

Revert `app.js` to `1mb`.

## confirmPassword accepted but never checked

The `changePasswordValidation` schema requires `confirmPassword` to be a non-empty string, and the frontend sends it. But `changePassword` in `auth.service.js` destructures only `{ currentPassword, newPassword }` — `confirmPassword` is discarded. The server changes the password even if the two fields disagree. Add a custom validator:

```js
body('confirmPassword')
  .custom((val, { req }) => val === req.body.newPassword)
  .withMessage('Password confirmation must match new password')
```

## Rate limiting gap on credential-checking endpoints

The auth routes apply `authLimiter` (10 attempts / 15 min, skip successful) to login, register, refresh, forgot-password, and reset-password. The new profile routes do not import or apply `authLimiter`. Since both `PUT /profile/email` and `PUT /profile/password` accept a `currentPassword` field and compare it against the stored hash, they are brute-force surfaces gated behind a valid access token but throttled only at the general rate limit (typically much higher than 10/15min). An attacker with a stolen or compromised session can probe the current password rapidly.

## Avatar storage and response-size inflation

Avatars are stored as full base64 data URLs in the `avatarUrl` field on the User document. A 5 MB JPEG becomes a ~6.67 MB string. Every call to `user.toJSON()` includes this field, and the application calls `toJSON()` in login, refresh, register, getProfile, updateProfile, changeEmail, changePassword, and uploadAvatar responses. The `AuthContext` on the frontend stores this in memory and re-serializes it into React state on every context update.

The `updateAvatar` repository method uses `findByIdAndUpdate` with `{ new: true }`, returning the full document including the base64 blob all the way to the HTTP response.

Consider either (a) storing the avatar in object storage / GridFS and persisting only a URL, or (b) adding `avatarUrl` to a `select('-avatarUrl')` pattern on most queries and providing it only through a dedicated `GET /profile/avatar` endpoint.

## Password validation regex drift

Backend (`profile.validation.js`):
```js
.matches(/[!@#$%^&*(),.?":{}|<>]/)
```

Frontend (`Profile.jsx`):
```js
/[!@#$%^&*(),.?":{}|<>[\]\\;'`~_+\-=/]/
```

The frontend set is a strict superset — it accepts semicolons, backticks, tildes, underscores, plus, minus, equals, forward-slash, backslash, and square brackets. A user who picks `Password1~` will see the green checkmark on the frontend and a 422 from the server. The regex should be defined in a single shared constant or at minimum kept in sync.

## Redundant route surface

Before this change, `PUT /api/auth/profile` handled name, organization, avatarUrl, preferences, and password change (via `currentPassword`/`newPassword` in the same payload). The new `PUT /api/profile` handles name and organization only, while email and password are broken into separate endpoints. Both routes remain active with different validation rules. The `updateProfileValidation` in `auth.validation.js` now also accepts data URLs in `avatarUrl` via the new custom validator — so the old route can still set avatars via URL. This creates a confusing surface where the same operation can be done two ways with different validation strictness.

## emailVerified lifecycle

The model gains an `emailVerified` field defaulting to `false`. On email change it's explicitly set to `false`. No endpoint sets it to `true` — there's no verification email, no token, no callback. Consumers that read `emailVerified` from the API response will always see `false`, which could be misleading if any authorization decision is ever gated on it.
